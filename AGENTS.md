# Инструкции для агентов

## Стилевые токены и переопределения

- Перед добавлением CSS-токена изучи существующие токены UI и используй подходящий по смыслу. Если подходящего токена нет, предложи новый по принятой системе именования и объясни, зачем он нужен.
- UI хранит значения палитры и общих стилей в глобальной теме под префиксом `--ui-`.
- В стилях компонентов первым указывается логически названный токен переопределения с префиксом `--app-`, вторым — соответствующий токен UI как fallback. Не дублируй значения UI палитры литералами в fallback.
- Сопоставляй токены `--app-*` и `--ui-*` по их смысловой роли, а не только по совпадению текущих значений. Токены разных ролей не взаимозаменяемы, даже если сейчас содержат одинаковое значение. Если подходящего токена UI нужной роли нет, предложи отдельный токен и объясни его назначение.
- Приложение переопределяет стиль, задавая токен `--app-` на корневом элементе или нужном контейнере. Токены `--ui-` задают значения по умолчанию и не используются для переопределения приложения.
- Тему UI нужно подключать глобально в каждом приложении, которое использует эти токены, включая host и Storybook.
- Брейкпоинты и другие значения, нужные Sass во время сборки, остаются Sass-переменными или миксинами.

## Формат commit message

- После завершения работы над отдельным блоком предложи commit message в формате `[type]: [feature] - [description]`.
- Используй только типы `feat` для новой функциональности, `style` для изменений стилистики, `refactor` для оптимизации, рефакторинга или декомпозиции, `config` для конфигурационных файлов и `docs` для документации.
- В `[feature]` указывай конкретную функцию или область изменений. Для общих изменений, не относящихся к отдельной функции, используй `common`.
- Если похожие доработки затрагивают разные функции, раздели их на отдельные коммиты по функциям и предложи сообщение для каждого.
- Пиши всё commit message строчными буквами.
